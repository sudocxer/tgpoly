# Телеграм-бот "Монополия" — техническая спецификация

Бот добавляется в группу и выполняет роль ведущего партии: поле, броски, деньги, собственность, обмен между игроками.

## 1. Базовые правила (упрощённая версия)

Взята классическая механика, из неё осознанно убрано:

- **Равномерная застройка группы** — строить дома можно на любой улице группы в любом порядке, без требования "сначала по одному на все".
- **Лимит домов/отелей в банке (32/12)** — не отслеживается, банк считается бесконечным.
- **Рента с коммуналок по броску кубиков** — заменена фиксированным множителем: одна коммуналка в собственности — рента ×4, обе — ×10.
- **Наценка 10% при снятии с ипотеки** — убрана, возвращается ровно заложенная сумма.
- **"Три дубля подряд — тюрьма"** — не применяется, дубль даёт обычный повторный бросок без ограничений.

Оставлено без изменений: покупка клеток по номиналу, рента с домов/отелей и вокзалов, налоговые клетки, карты Шанс/Казна, мортгейдж, банкротство и продажа построек банку при нехватке денег.

**Аукцион** при отказе от покупки — не убран, а сделан переключаемой опцией (вкл/выкл при создании партии).

## 2. Визуализация поля

Бот присылает в группу картинку поля в HD с аватарками игроков на клетках, соответствующих их текущей позиции. Обновляется после каждого хода (новый рендер, а не редактирование старого сообщения — правки картинок в HD через Bot API неудобны и медленны). Предыдущий рендер после этого удаляется ботом — в истории чата остаётся только актуальный (см. п.14).

## 3. Броски костей

- Используются **две** нативных телеграмных кости (`🎲`), а не одна — распределение суммы двух костей даёт колокол с пиком на 7, что ближе к оригинальному темпу игры и влияет на частоту посещения клеток.
- Нативный бросок кости в Telegram — это `message` с полем `dice`, отправляемое самим пользователем вручную, бот его только перехватывает (`message.dice`), инициировать бросок от лица бота нельзя.
- Проблема: в группе кто угодно может кинуть 🎲 не по делу. Решение — бот держит состояние "жду бросок от игрока X", игнорирует dice-события от всех прочих. Для двух костей отдельно закрывается окно между первым и вторым броском (тоже привязано к ожидаемому игроку).
- "Левые" броски (не от игрока, чей ход) бот **автоматически удаляет** — для этого боту нужны права администратора группы с разрешением на удаление сообщений.
- Если игрок, чей ход, вообще не бросает кости — см. п.6 (таймауты бездействия и голосование за пропуск).

## 4. Деньги и собственность

- Старт: фиксированная сумма (по умолчанию 1500, задаётся при создании партии).
- Покупка клетки — по номиналу, при отказе — либо аукцион (если опция включена), либо клетка остаётся у банка.
- Рента считается по стандартным правилам: с улиц — по таблице группы, удвоение при монополии без застройки, с вокзалов — по количеству вокзалов у владельца, с коммуналок — фиксированный множитель (см. п.1).

## 5. Рента и грейс-период

Если у игрока в момент списания ренты хватает наличных — списание происходит автоматически и мгновенно, без грейс-периода и подтверждений.

Если наличных не хватает — открывается **грейс-период**: окно времени, в течение которого должник может:
- продать дома банку за половину стоимости,
- заложить (mortgage) участок,
- договориться об обмене через `/swap`.

(Длительность окна, таймаут и голосование за досрочный пропуск — общая механика, см. п.6.)

Если долг не закрыт к концу окна, арендодателю (игроку, которому причитается рента) предлагается **принять весь оставшийся остаток имущества должника в денежном эквиваленте** — кэш + номинал/ипотечная стоимость незаложенной земли. Дома/отели в этот расчёт не входят: они к этому моменту уже проданы банку за половину стоимости (правило из п.1, без изменений) и учтены как кэш должника.

- Если арендодатель **соглашается** — происходит полная передача остатка имущества должника арендодателю (банкротство в пользу игрока, как в оригинальных правилах).
- Если арендодатель **отказывается** (или не реагирует, см. п.6) — банкротство в банк: всё оставшееся имущество должника возвращается банку (как при обычном банкротстве по долгу банку).

`/swap` при этом **не привязан к моменту оплаты ренты** — доступен в любой момент своего хода, как и в оригинальных правилах.

## 6. Таймауты бездействия и голосование за пропуск

Общая механика, применяется к трём разным окнам ожидания:
1. Окно должника в грейс-периоде (п.5) — продать дома / заложить участок / договориться об обмене.
2. Окно арендодателя — решение принять/отклонить остаток имущества должника (п.5).
3. Обычный ход игрока — ожидание броска костей (п.3), когда игрок вообще не реагирует.

Для каждого из трёх окон — по два независимых таймера. Оба задаются **админом вручную при создании партии, произвольным числом (не пресетом), отдельно для каждого типа окна**:

- **Таймаут окна** — по истечении бот применяет исход по умолчанию:
  - окно должника → переход к решению арендодателя;
  - окно арендодателя → автоотказ (банкротство в банк);
  - обычный ход → автопропуск хода, очередь переходит следующему игроку.
  
  Можно задать «без таймаута» (ждать бесконечно).
- **Задержка до голосования** — по истечении этой (обычно меньшей) задержки остальные активные игроки получают возможность голосованием досрочно завершить текущее окно, с тем же исходом по умолчанию, что и при обычном таймауте. Решается **простым большинством** от активных игроков (не считая самого бездействующего). Можно отключить.

## 7. Обмен между игроками

- **Инициировать `/swap` может только активный игрок** (чей сейчас ход) — с любым другим игроком в качестве второй стороны. Остальные игроки не могут открыть свою параллельную сделку; они могут быть целевой стороной чужой сделки, а вне этого — только неформально предлагать условия обычными сообщениями в чате (это не часть механики бота, просто договорённость между людьми).
- Если у активного игрока уже есть незавершённая сделка, перед тем как предложить размен другому игроку он должен сначала **отменить или завершить** старую. Из этого следует, что в игре одновременно не может быть больше **одной** открытой сделки — отдельный лимит не нужен.

### Текстовая версия (первый этап реализации)
`/swap @ник_игрока` — открывает интерфейс сделки.
- Подсказки: add/remove по каждой стороне.
- Показывается: количество денег + список объектов, которые есть у оппонента (что можно предложить/попросить).
- Можно менять деньги на участок и любые комбинации.
- Обмен происходит только после подтверждения **обеих** сторон.

### Более надёжный вариант того же текстового /swap
Вместо парсинга одной команды со всем синтаксисом — интерактивное сообщение с inline-кнопками, которое обе стороны редактируют "вживую" (добавил/убрал пункт — сообщение обновляется у обоих сразу). Кнопка "подтвердить" появляется только когда обе стороны зафиксировали свою часть сделки. Меньше риск рассинхрона, не нужно объяснять синтаксис.

### Telegram Mini App (более сложный, поздний этап)
Технически — обычная веб-страница (HTML/CSS/JS, любой фреймворк), открывается во встроенном WebView через `telegram-web-app.js` SDK. Даёт:
- тему оформления под клиента пользователя,
- `initData` — подписанные хешем токена бота данные пользователя (нужна HMAC-проверка на бэкенде, чтобы исключить подделку),
- нативные элементы: haptic-отклик, MainButton/BackButton.

Для live-обмена между двумя игроками **нельзя** использовать встроенный одноразовый `sendData` (закрывает приложение после отправки, годится для форм). Нужен прямой канал: свой бэкенд + фронтенд стучится в него по HTTP/WebSocket. Game state живёт только на сервере как единственный источник истины, mini app у каждого игрока лишь отражает его через WebSocket/поллинг — иначе гарантирован рассинхрон между клиентами.

Основная сложность mini app — не сам факт "сайт в вебвью" (это просто), а: (1) валидация `initData`, (2) синхронизация состояния между несколькими открытыми клиентами.

**Решение по этапам**: начинать с текстового /swap (интерактивные кнопки), mini app — отдельная фаза, если понадобится.

## 8. Административные функции

- **Добавление игрока в середине партии** — админ партии задаёт стартовую сумму денег вручную, произвольным числом, но не больше **50% от общей суммы в игре** на момент добавления (кэш всех текущих игроков + номинал/ипотечная стоимость их участков + полная стоимость построенных домов/отелей по цене постройки). Новый игрок встаёт на "Старт".
- **Передача партии другому пользователю** — переприсвоение управляющего telegram_id существующему игровому объекту (деньги, позиция, собственность остаются как есть, меняется только владелец аккаунта). Технически — правка одной ячейки `telegram_id` в листе `Игроки` (п.10): деньги/позиция/собственность ссылаются на устойчивый `game_player_id`, а не на `telegram_id`, так что остальные листы трогать не нужно.

## 9. Технические заметки для реализации

- Боту нужны права администратора в группе + разрешение удалять сообщения (для чистки левых бросков костей).
- Состояние партии — синхронный источник истины на бэкенде (то же требование, что и для mini app в п.7).
- Рендер поля — генерация изображения по шаблону с оверлеем аватарок по координатам клеток; пересчитывать/перерисовывать после каждого хода.
- Ключевая логика, где чаще всего ошибаются в подобных ботах: расчёт ренты по группам/монополиям с учётом текущей застройки, и обработка грейс-периода при недостатке средств (таймауты и голосование — настраиваемые параметры партии, см. п.6).

## 10. Технический стек и хранение данных

- **Язык:** Python.
- **Хранение данных:** Excel-файл (`.xlsx`) как персистентное хранилище — даёт админу возможность быстро и вручную поправить данные, если понадобится.
  - Авторитетное состояние активных партий держится **в памяти процесса**, не читаем/пишем Excel на каждое действие — `openpyxl` перезаписывает файл целиком, это и медленно, и небезопасно при падении бота посреди записи.
  - После каждого меняющего состояние действия — снэпшот текущего состояния в Excel (бэкап + возможность посмотреть/поправить руками).
  - Ручные правки в файле не подхватываются автоматически — нужна явная команда админа `/reload_state`, перечитывающая файл в память. Отсюда следует: ручная правка — точечная корректировка между действиями бота, не параллельное редактирование во время активной игры (иначе следующий автосейв бота затрёт правки админа) — то есть "не злоупотреблять".
- **Отдельный Excel-файл на каждую партию**, а не один общий файл на всего бота. Причины:
  - снэпшот после каждого действия перезаписывает файл **целиком** (см. выше) — с одним общим файлом на все партии любое действие в любой из них перезаписывало бы данные вообще всех партий разом; отдельные файлы держат это перезаписывание в рамках одной партии;
  - у имени **файла** лимиты мягче, чем у имени **листа** в Excel (31 символ, запрет на `: \ / ? * [ ]`) — файловая система разрешает практически любую разумную длину, запрещённых символов меньше (`\ / : * ? " < > |`), так что имя почти никогда не придётся обрезать;
  - внутри файла партии можно свободно распределять данные по нескольким листам без риска захламить общий файл лишними вкладками.
  - Файлы партий лежат в одной папке на сервере. Имя файла — **название группы + id** (например `МойЧат_g001.xlsx`), название очищается от запрещённых файловой системой символов.
  - Внутри файла партии — три листа: `Настройки`, `Игроки`, `Собственность`. Именам листов больше не нужен id партии — он уже есть в имени файла. При необходимости можно добавить дополнительные листы (например, отдельный лог транзакций).
  - **Отдельный файл-шаблон `default.xlsx`** с листом `Настройки` — база для новой партии (его же бот показывает как стартовые значения на шаге 2 визарда `/newgame`, см. п.13). Файл партии при создании — **копия `default.xlsx`**, после чего значения меняются под конкретную партию (через визард `/newgame` или вручную).
  
  Настройки задаются двумя равноправными путями, читающими/пишущими один и тот же файл: вручную — до запуска партии, либо через визард `/newgame` прямо в группе, где стартует партия.

- **Лист `Игроки`** — по строке на игрока: `game_player_id` (P1..P8, устойчивый внутренний ключ), `telegram_id`, имя/ник, деньги, позиция на поле (0-39), статус (активен/банкрот), флаг админа партии.
  - `game_player_id` — стабильный ключ, никогда не меняется. `telegram_id` — единственное, что меняется при **передаче партии другому пользователю** (п.8): деньги, позиция и собственность при этом трогать не нужно, потому что все они привязаны к `game_player_id`, а не напрямую к `telegram_id`.
  - Банкрот — статус, а не удаление строки: игрок остаётся в листе для истории партии, из активных (очередь хода, голосования по п.6) исключается по статусу.
- **Лист `Собственность`** — по строке на каждую покупаемую клетку поля (улицы, вокзалы, коммуналки): id клетки, название, группа, номинал, владелец (`game_player_id` или «Банк»), в залоге (TRUE/FALSE), застройка (0 — пусто, 1-4 — дома, 5 — отель; дом и отель одновременно невозможны).

## 11. Взаимодействие с игроками: команды и интерфейс

Где возможно — нативные механизмы Telegram вместо команд с ручным синтаксисом:

| Действие | Реализация |
|---|---|
| Бросок костей | Нативные `🎲` (п.3), не команда |
| Покупка клетки / отказ | Inline-кнопки «Купить за N» / «Отказаться» под авто-сообщением о попадании на клетку |
| Аукцион | Reply-сообщение с числом (ставка) — детали в п.12 |
| Постройка домов | `/build` → инлайн-список улиц с монополией, +/- по каждой |
| Ипотека / снятие | `/mortgage` → инлайн-список своих участков, переключатель «заложить/снять» |
| `/swap` | Без аргументов → инлайн-список остальных игроков (по имени/user_id, не по `@username`) → выбор цели кнопкой → конструктор сделки кнопками |
| Согласие арендодателя принять имущество должника | Сообщение с кнопками «Принять» / «Отклонить» |
| Голосование за пропуск (п.6) | Кнопка «Пропустить (N/M)» в чате, счётчик в тексте кнопки обновляется по клику |
| Свой статус (деньги/собственность) | `/me` |
| Повторно прислать текущее поле | `/board` |
| Создание/старт партии | `/newgame` → визард настроек + сбор игроков через Poll, детали в п.13 |
| Добавление игрока в середине партии | `/addplayer` (админ) |
| Передача управления партией | `/transfer` (админ) |
| Перечитать состояние из Excel после ручной правки | `/reload_state` (админ) |
| Меню команд в Telegram | `setMyCommands` — список команд с описанием во встроенном меню «/» |

**Почему `/swap` без `@username`:** не у всех пользователей Telegram есть публичный `@username` (только отображаемое имя) — команда с упоминанием на них не сработает. Раз уже решили делать надёжный вариант через кнопки (п.7), логично и выбор цели сделки сделать кнопкой, а не текстом — заодно ничего не нужно печатать руками.

**MVP работает только внутри одной группы** — весь лог партии (рендеры поля, крупные события) и все интерактивные действия идут в тот же чат, где создана партия. Режим «канал (чистый лог) + привязанная группа (взаимодействия)» — отдельная более поздняя фаза, добавляется по мере необходимости (аналогично Mini App в п.7): обработчики взаимодействий не меняются, поскольку реальный ввод от игроков физически происходит в привязанной к каналу discussion-группе в любом случае, меняется только куда уходит "чистый" лог.

## 12. Аукцион — детальный флоу

1. Активный игрок отказался от покупки клетки → бот шлёт сообщение в группу: клетка, стартовая цена от 1, «отвечайте (reply) числом».
2. Ставка — **reply с числом** на аукционное сообщение бота **или на любую другую ставку в этой же ветке** (например, ответ на чужую ставку, а не на исходное сообщение бота) — вся цепочка reply считается одним аукционом, не только прямые ответы на первое сообщение.
3. На каждый такой reply бот проверяет: текст — валидное число; число **строго больше** текущей лучшей ставки (сравнение всегда с единой текущей лучшей ставкой аукциона, а не с тем сообщением, на которое конкретно ответили); у ставящего **хватает наличных**. Невалидная ставка отклоняется (короткий ответ с причиной), текущая лучшая ставка не меняется.
4. Валидная ставка становится текущей лучшей, таймер тишины сбрасывается.
5. **Таймаут тишины** (настройка партии `auction_close_delay_sec`, по умолчанию 10 секунд — не константа, задаётся как остальные настройки, см. п.10) без новой валидной ставки после последней принятой → аукцион закрывается:
   - есть ставки → клетка уходит игроку с лучшей ставкой, деньги списываются в банк;
   - ставок не было → клетка остаётся у банка (как и при выключенном аукционе, п.4).
6. Участвовать может любой игрок партии, включая того, кто отказался от покупки по номиналу (как в оригинальных правилах).

Технически: бот хранит множество `message_id`, принадлежащих текущему аукциону — изначально в нём только id аукционного объявления. Входящий `message` считается попыткой ставки, если его `reply_to_message.message_id` входит в это множество; текст парсится как число и валидируется (п.3). При успешной ставке её `message_id` тоже добавляется в множество — так цепочка reply растёт на любую глубину, а не только прямыми ответами на исходное сообщение.

## 13. Запуск партии: визард `/newgame`

1. Игрок выполняет `/newgame` в группе → становится **админом партии**.
2. Бот присылает сообщение с текущими (дефолтными) настройками партии — стартовая сумма, вкл/выкл аукциона, три пары «таймаут окна + задержка до голосования» (должник / арендодатель / обычный ход, см. п.6) — с кнопкой **«Продолжить»** снизу.
3. До нажатия «Продолжить» админ может поменять любые значения без кнопок — **reply на это сообщение** текстом вида `имя_настройки значение` (можно несколько строк за один reply — по настройке на строку). После каждого такого reply бот **редактирует** то же сообщение с уже обновлёнными значениями.
4. Нажатие «Продолжить» фиксирует настройки (пишутся в лист настроек Excel, п.10) и запускает сбор игроков:
   - бот шлёт **нативный Telegram Poll** (не анонимный, чтобы видеть, кто именно ответил) с вариантами «Да» / «Нет»;
   - проголосовавшие «Да» становятся игроками партии; смену голоса (Да↔Нет) бот отслеживает через `poll_answer` и обновляет список игроков соответственно;
   - **минимум 2, максимум 8** игроков;
   - при единственном голосе «Да» партия стартовать не может;
   - при достижении 8 — партия стартует автоматически, без дополнительных действий;
   - начиная с 2 и до 8 голосов — админ партии может запустить партию досрочно: **reply на сообщение с poll текстом «start»**, либо кнопкой **«Start»** под отдельным сообщением бота (реагирует только на клик самого админа партии, остальные клики игнорируются).

## 14. Гигиена сообщений и логирование

- **Удаление устаревших сообщений бота.** Не всё подряд: сообщения, зафиксировавшие событие, реально повлиявшее на партию (покупка, начисление ренты, банкротство, завершённая сделка, итог аукциона), **остаются** в истории чата навсегда. А вот старые версии одного и того же процессного сообщения в пределах одной сессии — например, предыдущий рендер поля после следующего хода (п.2), или предыдущая версия сообщения с настройками `/newgame`, если её пришлось переслать заново, а не отредактировать, — бот подчищает, актуальна только последняя версия.
- **Файловый лог партии.** Отдельно от Excel-снэпшота состояния — один лог-файл на партию на сервере (например `logs/<game_id>.log`), для отладки и разбора инцидентов. Доступен только **оператору бота** (тому, кто развернул и обслуживает самого бота — не путать с админом партии, это игровая роль внутри одной группы), в Telegram не публикуется.
